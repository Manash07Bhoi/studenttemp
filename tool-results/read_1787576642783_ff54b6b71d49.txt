    10→    10→# 📄 FILE: `PRD.md`
    11→    11→
    12→    12→## 1. Product Summary
    13→    13→
    14→    14→StudentTemp is a privacy-first temporary email platform built for students, developers, testers, and privacy-conscious users. It issues short-lived, disposable inboxes with **real SMTP receiving**, sanitized HTML rendering, automatic expiration, and a mobile-first PWA experience. It never impersonates real institutional (`.edu`, `.ac.in`) identity.
    15→    15→
    16→    16→**Core Loop:** `Open → Generate/Customize → Copy → Receive → Read → Expire/Delete`
    17→    17→
    18→    18→## 2. Goals / Non-Goals
    19→    19→
    20→    20→Same as baseline spec (see canonical list). Key reinforced rule:
    21→    21→
    22→    22→> ❌ Never issue, forge, or imply real university/school (`.edu`, `.ac.in`, `.edu.in`) addresses.
    23→    23→> ✅ May offer **operator-owned, India-themed domains** (e.g. `@studentbox.in`, `@campusmail.in`) purely as branding — clearly labeled "temporary, not an official institution address."
    24→    24→
    25→    25→## 3. Headline New Features (this revision)
    26→    26→
    27→    27→### 3.1 Custom Email Alias (Customization Engine)
    28→    28→- User can request a **custom local-part** instead of a random one: `rahul.dev@studentbox.in`
    29→    29→- Availability check in real time (debounced, rate-limited)
    30→    30→- Rules: 3–30 chars, `a–z 0–9 . _ -`, no leading/trailing symbol, no reserved words (`admin`, `support`, `postmaster`, `abuse`, `security`, `noreply`, `webmaster`), profanity/slur filter, no impersonation patterns (`paypal-support`, `bank-verify`, etc.)
    31→    31→- Custom aliases still **expire** like random ones (customization ≠ permanence)
    32→    32→- Anti-squatting: same custom alias cannot be re-claimed by a different anonymous session for a cooldown window after expiry (prevents targeted hijack of "waited-for" addresses)
    33→    33→
    34→    34→### 3.2 "Indian Student" Themed Domain Pack
    35→    35→- Curated, operator-owned `.in`/`.co.in` style domains with student-friendly branding: `@studentbox.in`, `@campusmail.in`, `@examprep.in`
    36→    36→- Regional language UI (Hindi, Odia, Telugu, Tamil, Bengali, Marathi)
    37→    37→- Category presets tuned to Indian student use cases: *Exam Portal Registration*, *Scholarship Portal*, *Coaching App OTP*, *College Fest Signup*, *Internship Portal*
    38→    38→- Persistent, prominent disclaimer banner: *"This is a private temporary address, not an official school/college/university email."*
    39→    39→- No claim of `.edu.in`/`.ac.in` affiliation anywhere in UI, marketing, or metadata.
    40→    40→
    41→    41→### 3.3 Multi-Address Management ("My Addresses" Tray)
    42→    42→- Up to N (policy-defined, e.g., 5 for free/anonymous session) concurrently active inboxes per session token
    43→    43→- Quick switcher (bottom sheet on mobile, sidebar on desktop)

    78→    78→# 📄 FILE: `AGENT.md` (Instructions for AI Coding Agent)
    79→    79→
    80→    80→## Purpose
    81→    81→This file governs any AI agent (Copilot/agentic coder) contributing code to this repository. It is a **binding contract**, not a suggestion.
    82→    82→
    83→    83→## 1. Absolute Prohibitions
    84→    84→The agent **must never**:
    85→    85→- Insert mock, placeholder, dummy, or fake data into any file that ships to staging/production.
    86→    86→- Write `// TODO`, `// FIXME`, `// placeholder`, `console.log` debug leftovers, or stub functions that silently "pretend" to work.
    87→    87→- Simulate SMTP, fake "message received" events, or hardcode sample inbox content.
    88→    88→- Fabricate malware-scan results, SPF/DKIM/DMARC results, or analytics numbers.
    89→    89→- Hardcode secrets, API keys, DB passwords, or JWT signing keys in source.
    90→    90→- Generate fake `.edu`/`.ac.in`/institutional domains or claim official student-identity status anywhere in copy, metadata, or code comments.
    91→    91→- Disable security checks "temporarily" without an explicit, tracked, expiring ticket.
    92→    92→- Ship a feature without: input validation, error state, loading state, empty state, and a test.
    93→    93→
    94→    94→If a real dependency (SMTP server, malware scanner, object storage) is not yet available in the dev environment, the agent must build against a **clearly isolated, explicitly labeled local test harness** inside `/tests/fixtures`, never inside `/apps` or `/services` production code paths, and must leave a real integration point (interface/contract) ready to wire up — not a fake success return baked into business logic.
    95→    95→

    97→    97→1. Correctness of mail-receiving pipeline
    98→    98→2. Security (sanitization, isolation, auth, rate limiting)
    99→    99→3. Data lifecycle correctness (expiration really deletes data)
   100→   100→4. Reliability/observability
   101→   101→5. UX polish
   102→   102→6. Visual design
   103→   103→
   104→   104→## 3. Tech Stack Contract
   105→   105→
   106→   106→| Layer | Technology | Reason |
   107→   107→|---|---|---|
   108→   108→| Frontend | TypeScript, React, Vite, PWA | Free hosting compatible, fast DX |
   109→   109→| BFF / Public API | TypeScript (Node, Fastify or Hono) | Shares types with frontend, fast to iterate |
   110→   110→| Mail Gateway & Security Core | Go | High concurrency SMTP handling, strong stdlib crypto/net |
   111→   111→| Database | PostgreSQL (Neon/Supabase free tier) | Relational integrity, TTL-friendly, JSONB for metadata |
   112→   112→| Cache/Queue | Redis (Upstash free tier) | Rate limiting, pub/sub for real-time push, TTL keys |
   113→   113→| Object Storage | Cloudflare R2 free tier / Supabase Storage | Attachment blobs |
   114→   114→| Real-time transport | SSE (primary), WebSocket (fallback upgrade later) | Simpler infra, unidirectional fits use case |
   115→   115→| Reverse Proxy / Edge | Cloudflare (free plan) | WAF, CDN, DDoS protection, free TLS |
   116→   116→| Inbound Email | Cloudflare Email Routing → Worker → API webhook, OR self-hosted Postfix on Oracle Cloud Always-Free VM | Zero-cost inbound SMTP path |
   117→   117→| CI/CD | GitHub Actions (free minutes for public/small private repos) | No cost |
   118→   118→| Hosting (frontend) | Cloudflare Pages / Vercel free tier | Free, fast global CDN |
   119→   119→| Hosting (API/Go services) | Fly.io free allowance or Oracle Cloud Free Tier VM | Free compute |
   120→   120→
   121→   121→**Rule:** Do not introduce Kubernetes, Kafka, microservice sprawl, or additional languages unless a measurable requirement (documented in an ADR under `/docs/architecture/adr/`) justifies it.
   122→   122→
   123→   123→## 4. Coding Standards
   124→   124→- Strict TypeScript (`strict: true`, no `any` without justification comment + lint-suppression review).
   125→   125→- Go: `golangci-lint` clean, context-aware cancellation on all I/O, no goroutine leaks.
   126→   126→- All public functions documented (purpose, inputs, outputs, error modes).
   127→   127→- All user input validated at the boundary (API layer) using schema validation (e.g., Zod) — never trust client.
   128→   128→- All DB access via parameterized queries only — never string-concatenated SQL.
   129→   129→- All secrets read from environment/secret manager, never committed. `.env.example` only, never `.env`.

   177→   177→## Screen 1 — Splash / App Boot
   178→   178→**Purpose:** Cold start, session bootstrap.
   179→   179→**UI:** Centered logo mark, subtle pulse animation (respecting reduced-motion), version tag bottom.

   186→   186→**Sections (top→bottom):**
   187→   187→1. Hero card: current address (monospace, truncation-safe), Copy, QR, Share, Regenerate
   188→   188→2. Expiry chip with live countdown + color states (Normal=neutral, Warning ≤15min=amber, Critical ≤1min=red, Expired=gray)

   192→   192→**Loading State:** Skeleton rows (3) mimicking message card shape; hero card shows skeleton for address if still generating.

   195→   195→- Tap Copy → clipboard write → toast "Copied" (2s) + subtle button pulse

   410→   410→## Firebase Usage Note
   411→   411→Core data (inboxes/messages) lives in PostgreSQL, **not** Firebase, for relational integrity and full control over deletion lifecycle. Firebase (free Spark plan) is used **only** for two optional, non-sensitive capabilities: (1) Web Push relay via **FCM**, (2) lightweight anonymous **Firestore** doc used purely as a real-time "inbox has new mail" ping mirror for browsers where SSE is blocked by network policy (a fallback signal only — never the source of truth, never stores message content).
   412→   412→
   413→   413→### Firestore Data Model (fallback signal only)
   414→   414→```
   415→   415→/inboxPings/{publicInboxId}
   416→   416→    lastMessageAt: timestamp
   417→   417→    unreadCount: number
   418→   418→    expiresAt: timestamp
   419→   419→```
   420→   420→No message content, sender data, or PII ever written here.
   421→   421→
   422→   422→### Firestore Security Rules (conceptual, to adapt in `firestore.rules`)
   423→   423→```
   424→   424→rules_version = '2';

   426→   426→  match /databases/{database}/documents {
   427→   427→
   428→   428→    match /inboxPings/{inboxId} {
   429→   429→      // Clients may only read the ping doc for an inbox they can prove
   430→   430→      // knowledge of via a signed, short-lived custom token minted by
   431→   431→      // the backend after validating session ownership.
   432→   432→      allow read: if request.auth != null
   433→   433→                  && request.auth.token.inboxId == inboxId;
   434→   434→

   436→   436→      allow write: if false; // writes happen exclusively via Admin SDK

   438→   438→

   452→   452→## App Lock Flow (Logic Description — No Code)
   453→   453→
   454→   454→**Purpose:** Protect the *local device UI session* (not the server data) from casual shoulder-surfing/unauthorized phone access, since a temp inbox can contain sensitive OTPs.
   455→   455→
   456→   456→**Setup flow:**
   457→   457→1. User enables "App Lock" in Settings.
   458→   458→2. Client checks for platform biometric availability (WebAuthn platform authenticator). If available, offers "Use biometric" as primary, PIN as fallback. If unavailable, PIN-only.
   459→   459→3. PIN (4–6 digits) is never stored in plaintext or transmitted to the server. It is used to derive a local key (e.g., via a slow key-derivation function) that encrypts a small local "unlock marker" stored in browser storage. The server has no knowledge of the PIN and cannot reset it — it is purely a local gate.
   460→   460→4. A "Forgot PIN" action clears local encrypted state only; it does **not** delete or affect the server-side inbox, which continues to exist until its own expiration.
   461→   461→
   462→   462→**Unlock flow (on app resume / cold start when lock enabled):**
   463→   463→1. App detects lock flag in local state on load, before rendering inbox content — shows the Lock screen immediately, blocking rendering of any message data underneath (data is not fetched/rendered until unlocked, to avoid flash-of-content).
   464→   464→2. User authenticates via biometric prompt or PIN pad.
   465→   465→3. On success: unlock marker is validated locally, session resumes exactly where left off, and the inbox data fetch proceeds.
   466→   466→4. On repeated failure (e.g., 5 attempts): a temporary cool-down timer is enforced locally (progressively increasing delay) to slow brute-force PIN guessing; it does not lock the user out of the server-side inbox (they could still recover via the session token page from another device if truly locked out locally).
   467→   467→5. **Auto-lock triggers:** app backgrounded for > configurable idle threshold (default 2 minutes), manual "Lock now" action, or device screen lock detected via visibility API.
   468→   468→6. App Lock is a **client-side convenience/privacy feature**, explicitly documented as not a substitute for account security, since there is no traditional account.
   469→   469→
   470→   470→## Threat Model
   471→   471→(As baseline T1–T7, retained) plus:
   472→   472→
   473→   473→**T8 — Custom Alias Enumeration/Squatting:** Attacker scripts alias-availability checks to scrape desirable names or repeatedly claims-and-abandons popular names. Mitigation: per-IP/session rate limit on availability checks, cooldown ledger (`custom_aliases` table), CAPTCHA escalation after N checks/minute.
   474→   474→
   475→   475→**T9 — Fallback Firestore Channel Abuse:** Attacker attempts to read ping data for inboxes they don't own. Mitigation: custom-token minting scoped to a single `inboxId` claim, short TTL, rules deny-by-default.
   476→   476→
   477→   477→**T10 — App-Lock Bypass via DevTools:** Local-only lock is inherently bypassable by a technical local attacker with device access; mitigated by clearly scoping App Lock as anti-shoulder-surfing, not a cryptographic guarantee, and by never storing decrypted message bodies in a way retrievable without the normal fetch+render path (in-memory only, not persisted unencrypted to disk/localStorage).

   495→   495→# 📄 FILE: `WORKFLOWS.md` (App Logic Behavior — Described, Not Coded)
   496→   496→
   497→   497→## Inbox Generation Flow
   498→   498→1. Client requests a new inbox (no auth required for anonymous default).
   499→   499→2. Server generates a cryptographically random local-part with sufficient entropy, checks uniqueness against active inboxes for the chosen domain, and creates a session if none exists (returns a session token to store client-side, hashed copy stored server-side).
   500→   500→3. Server sets `expires_at` per selected/default preset, inserts the inbox row, warms the Redis cache entry, and returns the public inbox identifier + address + expiry to the client.
   501→   501→4. Client stores the session token securely (never exposes it in the URL) and opens an SSE connection scoped to that inbox's public ID.
   502→   502→
   503→   503→## Custom Alias Claim Flow
   504→   504→1. Client types a desired local-part; client debounces and calls the availability check endpoint.
   505→   505→2. Server validates format, checks reserved-word/profanity list, checks `custom_aliases` cooldown ledger, checks current `inboxes` table for active conflicts, and returns availability plus a short-lived reservation token if available.
   506→   506→3. On confirm, client submits the reservation token; server re-validates atomically (transaction with row lock) to prevent race conditions between two users claiming the same name simultaneously, then creates the inbox.
   507→   507→4. On expiry of a custom-alias inbox, the ledger records a cooldown window before the same name becomes claimable again.
   508→   508→
   509→   509→## Real-Time Mail Delivery Flow
   510→   510→1. Inbound SMTP connection hits the Mail Gateway; recipient is validated against active, non-expired inboxes before accepting the message (rejects unknown/expired recipients early to reduce backscatter and storage waste).
   511→   511→2. Accepted message is queued; Mail Processor parses MIME, extracts headers, computes SPF/DKIM/DMARC results (from received headers/environment, not fabricated), sanitizes HTML, stores sanitized HTML and any attachments in object storage, and inserts DB rows.
   512→   512→3. Processor publishes an event on the Redis pub/sub channel scoped to the inbox's public ID.
   513→   513→4. Any connected SSE client subscribed to that channel receives a lightweight "new message" event and requests the updated message list via the API (avoids pushing full content over the real-time channel unnecessarily).
   514→   514→5. If no client is connected, the Firestore fallback ping (if enabled) is updated so a reconnecting client or push notification can reflect the new state.
   515→   515→
   516→   516→## Expiration & Cleanup Flow
   517→   517→1. A scheduled cleanup worker continuously scans the partial index of active inboxes nearing/past `expires_at`.
   518→   518→2. At the warning thresholds (15 min / 5 min / 1 min remaining), the server does not need to push anything extra — the client computes and displays countdown locally from the authoritative `expires_at` timestamp, re-synced periodically to correct clock drift.
   519→   519→3. At expiry, the inbox status transitions to `expired`; a grace-restore window may apply per policy (single use, rate-limited) allowing a short extension if requested before hard deletion.
   520→   520→4. After the grace window (or immediately if none applies), the cleanup worker deletes attachments from object storage first, confirms deletion, then deletes DB rows for attachments, messages, and finally the inbox row (or soft-marks and purges on a delayed final sweep, per the documented retention policy), invalidates the Redis cache entry, and removes any Firestore ping doc.
   521→   521→5. Cleanup emits an audit-style internal metric (counts only, no content) for observability.
   522→   522→
   523→   523→## Abuse Detection & Response Flow
   524→   524→1. Every inbound request (API and SMTP) is scored using layered signals: IP reputation, request rate over sliding windows, behavioral anomalies (e.g., rapid sequential availability checks), and session risk history.
   525→   525→2. Low risk → allowed normally. Medium risk → challenge (e.g., proof-of-work or CAPTCHA) inserted before the action completes. High risk → request blocked and an `abuse_events` record is written (hashed IP only).
   526→   526→3. Persistent high-risk sources accumulate a reputation penalty that can escalate to temporary IP/subnet blocking at the edge (Cloudflare WAF rule), independent of the application layer, for defense-in-depth.
   527→   527→4. Domain-level abuse (e.g., a specific operator domain attracting spam/backscatter complaints) can be disabled independently via the Domain kill-switch without affecting other domains or the whole service.
   528→   528→
   529→   529→## App Lock Flow
   530→   530→Described in full in `SECURITY.md` above.
   531→   531→
   532→   532→## Notification Flow
   533→   533→1. User opts in to notifications; client requests browser permission and registers a push subscription, sent to the server and stored against the current session.
   534→   534→2. On new-message events, the Notification Service sends a minimal, content-free push payload ("New email received in student-xxxx@...") respecting the user's preview preference.
   535→   535→3. Tapping the notification deep-links directly to the relevant inbox/message screen, re-validating session ownership before rendering.
   536→   536→
   537→   537→## Error Handling Philosophy
   538→   538→Every user-facing failure must (a) explain what happened in plain language, (b) offer a concrete next action (Retry / Create New / Go Home), and (c) log a correlation/request ID visible to the user for support purposes, without ever exposing stack traces, internal IDs, or sensitive diagnostic data in the UI.
